# Техническое задание

Проект клиента браузера на Python с использованием patchright.

## 1. Назначение проекта
Клиент предназначен для программного и консольного запуска браузера с настраиваемыми параметрами окружения, профиля и сетевого подключения.

## 2. Основные возможности
- Консольный интерфейс для запуска браузинга и открытия тестовых страниц с ключами.
- HTTP API для удаленного запуска сценариев.
- Возможность запуска в Docker.
- Поддержка задания произвольного User-Agent.
- Возможность работы с SOCKS5-прокси через утилиту socks2http.
- Возможность создания, загрузки и хранения профиля с указанным именем и по указанному пути.
- Возможность получения cookies активной страницы и браузерного контекста.
- Возможность получения HTTP headers запроса и ответа для открываемых страниц.
- Возможность получения содержимого страницы после полной или частичной загрузки DOM.
- Возможность интерактивного браузинга через API: поиск элементов, клик, ввод текста, выбор значений, отправка форм.
- Возможность управления мышью через API: прокрутка страницы, перемещение курсора, в том числе по случайной траектории.

## 3. Функциональные требования
### 3.1 Запуск браузера
- Поддержка headless и headful режимов.
- Возможность открытия одной или нескольких страниц по URL.
- Возможность передачи дополнительных параметров запуска браузера.
- Возможность ожидания полной загрузки страницы или указанного события перед сбором данных.

### 3.2 Работа с профилями
- Создание нового профиля по имени.
- Загрузка существующего профиля из указанной директории.
- Хранение cookies, localStorage и других пользовательских данных.
- Проверка существования профиля перед запуском.

### 3.3 Работа с User-Agent
- Установка User-Agent через CLI и API.
- Использование значения по умолчанию, если параметр не передан.

### 3.4 Работа с прокси
- Поддержка SOCKS5 через socks2http.
- Возможность передавать адрес, порт, логин и пароль прокси.
- Проверка доступности прокси перед стартом браузера.

### 3.5 Получение данных страницы
- Возможность получать cookies после открытия страницы или выполнения сценария.
- Возможность получать headers исходящего запроса и headers ответа страницы.
- Возможность получать HTML-содержимое страницы целиком.
- Возможность, при необходимости, получать текстовое содержимое страницы без HTML-разметки.
- Возможность сохранять полученные данные в stdout, файл или возвращать через API.
- Возможность ограничивать объем сохраняемого содержимого и маскировать чувствительные заголовки.

### 3.6 Взаимодействие со страницей
- API должен поддерживать поиск элементов по CSS-селектору, XPath, `id`, `name`, `class`, тексту и атрибутам.
- API должен поддерживать поиск одного элемента и списка элементов.
- API должен поддерживать проверку существования элемента, его видимости, доступности для клика и состояния `disabled`.
- API должен поддерживать действия `click`, `dblclick`, `hover`, `focus` и `press` для найденного элемента.
- API должен поддерживать ввод текста в поля формы, очистку поля, выбор значения в `select`, установку и снятие `checkbox` и `radio`.
- API должен поддерживать отправку формы как через клик по кнопке отправки, так и через вызов submit-сценария или нажатие `Enter`.
- API должен поддерживать управление мышью: перемещение курсора к координатам или элементу, вертикальную и горизонтальную прокрутку, прокрутку до элемента и случайное движение курсора в пределах страницы или заданной области.
- API должен поддерживать настройку параметров движения мыши: количество промежуточных шагов, задержку, диапазон случайного отклонения и ограничение области движения.
- API должен поддерживать ожидание появления элемента, изменения состояния DOM, завершения навигации и сетевой активности после действия.
- API должен поддерживать возврат результата действия: признак успеха, сведения о найденном элементе, текст, атрибуты и диагностические ошибки.

## 4. CLI-интерфейс
CLI должен поддерживать запуск из терминала Linux.

### 4.1 Запуск сценариев через CLI
- CLI должен поддерживать запуск простых сценариев из YAML- или JSON-файла.
- Команда запуска сценария должна иметь вид `autobrowser run-script --file scenario.yaml`.
- Сценарий должен позволять описывать параметры сессии браузера, открываемые страницы и последовательность действий.
- Для простых сценариев должен использоваться декларативный формат без циклов, условных операторов и пользовательских функций.
- Перед выполнением сценарий должен проходить валидацию с возвратом понятных диагностических ошибок.
- Должны поддерживаться режимы остановки при первой ошибке и продолжения выполнения с возвратом результата по каждому шагу.

### 4.2 Поддерживаемые действия сценария
- Открытие страницы: `open`.
- Ожидание события, состояния DOM или таймера: `wait`.
- Поиск элемента: `find`.
- Действия с элементом: `click`, `dblclick`, `hover`, `focus`, `fill`, `clear`, `select`, `check`, `uncheck`, `press`, `submit`.
- Действия мышью: `move`, `scroll`, `move-random`.
- Получение данных: `get-content`, `get-cookies`, `get-headers`, `get-attributes`, `get-text`.
- Сохранение результата в stdout или файл: `save`.

### 4.3 Требования к формату сценария
- Сценарий должен поддерживать секции `session`, `pages`, `steps` и `output`.
- В секции `session` должны поддерживаться параметры `headless`, `profile`, `profileDir`, `userAgent`, `proxy`, `timeout` и дополнительные параметры запуска браузера.
- Каждый шаг в `steps` должен содержать тип действия `action` и набор параметров, необходимых для этого действия.
- Для шагов, работающих с DOM, должен использоваться единый формат локатора, совместимый с HTTP API.
- Должна поддерживаться настройка `stopOnError` на уровне всего сценария и, при необходимости, на уровне отдельного шага.
- Результат выполнения сценария должен включать общий признак успеха, длительность и результат по каждому шагу.

### 4.4 Валидация и схема сценария
- Для формата сценариев должна быть подготовлена JSON Schema для валидации YAML- и JSON-файлов до запуска.
- Схема должна описывать обязательные и опциональные поля корневого объекта, секций `session`, `pages`, `steps` и `output`.
- Для каждого типа действия в `steps` схема должна определять минимально необходимый набор полей, например `url` для `open`, `locator` для `find` и `click`, `value` для `fill`, `key` для `press`.
- Схема должна запрещать неизвестные типы действий и некорректные значения перечислений, включая типы локаторов и значения `waitUntil`.
- CLI должен поддерживать отдельный режим проверки сценария без запуска браузера, например `autobrowser validate-script --file scenario.yaml`.
- При ошибке валидации CLI должен возвращать код завершения, указывать путь до проблемного поля и краткое описание причины ошибки.

### Пример команды
`autobrowser run --url https://example.com --profile test1 --user-agent "Mozilla/5.0"`

### Пример запуска сценария
`autobrowser run-script --file scenario.yaml`

### Основные аргументы
- `--url` — URL для открытия
- `--profile` — имя профиля
- `--profile-dir` — путь к директории профилей
- `--user-agent` — строка User-Agent
- `--proxy` — параметры прокси
- `--headless` — запуск без UI
- `--timeout` — таймаут запуска и открытия страниц
- `--output-cookies` — вывести или сохранить cookies
- `--output-headers` — вывести или сохранить headers
- `--output-content` — вывести или сохранить содержимое страницы
- `--output-file` — путь к файлу для сохранения результата
- `--content-format` — формат содержимого: `html` или `text`
- `--file` — путь к YAML- или JSON-сценарию

### Пример YAML-сценария
```yaml
session:
  headless: true
  profile: test1
  userAgent: Mozilla/5.0
  timeout: 10000

steps:
  - action: open
    url: https://example.com/login

  - action: fill
    locator:
      type: name
      value: username
    value: demo-user

  - action: fill
    locator:
      type: name
      value: password
    value: demo-password

  - action: click
    locator:
      type: css
      value: button[type='submit']

  - action: wait
    waitUntil: networkidle

  - action: get-content
    format: html

output:
  file: result.html
```

### Минимальные требования к JSON Schema
```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "properties": {
    "session": {
      "type": "object"
    },
    "pages": {
      "type": "array"
    },
    "steps": {
      "type": "array",
      "minItems": 1
    },
    "output": {
      "type": "object"
    },
    "stopOnError": {
      "type": "boolean"
    }
  },
  "required": ["steps"],
  "additionalProperties": false
}
```

## 5. HTTP API
API должен предоставлять возможность:
- запускать браузер с параметрами;
- создавать профиль;
- получать статус процесса;
- завершать активную сессию;
- получать cookies, headers и содержимое страницы в ответе API или отдельным запросом.
- выполнять действия интерактивного браузинга над DOM-элементами страницы.

### Требования безопасности API
- API должен поддерживать привязку к конкретному адресу, включая `127.0.0.1` по умолчанию.
- Должна быть предусмотрена опциональная защита API через токен доступа или иной механизм аутентификации, задаваемый через конфигурацию.
- При включенной аутентификации все запросы, кроме healthcheck, должны проверяться до выполнения операций с браузером.
- В логах и ответах API не должны возвращаться секреты, токены, пароли прокси и полные значения чувствительных заголовков.
- Должно поддерживаться ограничение количества одновременно активных сессий и запросов к API.

### Жизненный цикл сессии
- Каждая сессия браузера должна иметь уникальный идентификатор и явные состояния: `starting`, `running`, `stopping`, `stopped`, `failed`.
- Должен поддерживаться таймаут бездействия сессии с автоматическим завершением и освобождением ресурсов.
- При штатном завершении или ошибке должны корректно освобождаться браузерный процесс, временные файлы, сетевые ресурсы и блокировки профиля.
- Должна поддерживаться принудительная остановка зависшей сессии через API или внутренний watchdog-механизм.
- После завершения сессии должна сохраняться диагностическая информация: время старта, время завершения, причина остановки, код ошибки при наличии.

### Версионирование API
- HTTP API должен иметь версионированный префикс, например `/api/v1`.
- Изменения, нарушающие обратную совместимость, должны вноситься только в новую версию API.

### OpenAPI-описание
- Для HTTP API должна быть подготовлена машиночитаемая спецификация OpenAPI.
- OpenAPI-описание должно включать все основные endpoints, схемы запросов, схемы ответов и коды ошибок.

### Общие требования к API браузинга
- Все операции браузинга должны выполняться в рамках активной сессии браузера.
- Запрос должен позволять указать `pageId` или URL страницы, если в сессии открыто несколько страниц.
- Для поиска элемента должен поддерживаться единый объект локатора с полями `type` и `value`, где `type` принимает значения `css`, `xpath`, `id`, `name`, `class`, `text`, `attribute`.
- Для операций ожидания должен поддерживаться параметр `timeout` и, при необходимости, `waitUntil` со значениями `domcontentloaded`, `load`, `networkidle`, `visible`, `hidden`.
- Ответ API должен содержать `success`, `sessionId`, `pageId`, `action`, `durationMs` и объект `result` или `error`.

### Операции браузинга
- Поиск элемента: получить один элемент или список элементов по заданному локатору.
- Чтение элемента: получить текст, HTML-фрагмент, атрибуты, текущее значение поля и состояние видимости.
- Клик по элементу: обычный клик, двойной клик, клик с модификаторами.
- Взаимодействие с формами: заполнение полей, очистка, выбор опций, установка флагов, отправка формы.
- Управление мышью: перемещение курсора по координатам или к элементу, прокрутка страницы и генерация случайной траектории движения.
- Клавиатурные действия: нажатие клавиш, в том числе `Enter`, `Tab`, `Escape`.
- Выполнение цепочки действий: несколько последовательных операций в одном запросе с единым результатом.

### Примеры операций
- `POST /api/v1/session/{id}/pages/{pageId}/elements/find` — найти элемент по локатору и вернуть его метаданные.
- `POST /api/v1/session/{id}/pages/{pageId}/elements/click` — выполнить клик по элементу с опциональным ожиданием навигации.
- `POST /api/v1/session/{id}/pages/{pageId}/elements/fill` — ввести текст в поле формы.
- `POST /api/v1/session/{id}/pages/{pageId}/forms/submit` — отправить форму по локатору формы или кнопки отправки.
- `POST /api/v1/session/{id}/pages/{pageId}/mouse/move` — переместить курсор к заданным координатам или центру найденного элемента.
- `POST /api/v1/session/{id}/pages/{pageId}/mouse/scroll` — выполнить прокрутку страницы или контейнера на указанное смещение либо до целевого элемента.
- `POST /api/v1/session/{id}/pages/{pageId}/mouse/move-random` — выполнить случайное движение курсора по заданной области с ограничением по длительности и амплитуде.
- `POST /api/v1/session/{id}/pages/{pageId}/actions/run` — выполнить массив действий, например `find`, `click`, `fill`, `press`, `submit`.

### Требования к телу запросов
- Для операций поиска и действий над элементами тело запроса должно содержать локатор элемента и опциональные параметры ожидания.
- Для `fill` должен передаваться текст или значение поля.
- Для `select` должно поддерживаться указание значения, текста опции или индекса.
- Для операций мыши должно поддерживаться указание координат, целевого элемента, смещения прокрутки, количества шагов, длительности и параметров случайного отклонения.
- Для `press` должно передаваться имя клавиши и, при необходимости, модификаторы.
- Для `actions/run` тело запроса должно содержать массив шагов с указанием типа действия и его параметров.

### Требования к ответам API браузинга
- При успешном поиске должен возвращаться идентификатор элемента, используемый в рамках текущего запроса или цепочки действий.
- При чтении элемента должны возвращаться текст, атрибуты, HTML или значение поля по запросу клиента.
- При выполнении действия должен возвращаться факт выполнения, длительность, сведения о пост-действии и, при необходимости, обновленный URL страницы.
- Для операций мыши должны возвращаться итоговые координаты курсора, фактическое смещение прокрутки и сведения об области, в пределах которой выполнялось движение.
- При частичном выполнении сценария `actions/run` должен возвращаться результат по каждому шагу.

### Примеры JSON-ответов

#### Успешный ответ для поиска элемента

## 6. Docker
Проект должен запускаться в контейнере Docker.

### Требования
- Docker-образ приложения должен быть основан на `Ubuntu 24.04`.
- Сборка и запуск проекта должны поддерживаться через `docker compose`.
- Dockerfile для сборки приложения.
- Контейнер должен содержать все системные зависимости, необходимые для запуска браузера, patchright и сопутствующих утилит.
- Приложение внутри контейнера должно запускаться с непривилегированным пользователем, если это не противоречит требованиям запуска браузера.
- Возможность передачи параметров через переменные окружения.
- Поддержка volume для хранения профилей, временных браузерных данных и служебных файлов.
- Возможность проброса API-порта наружу.
- Контейнер должен иметь healthcheck для проверки готовности HTTP API.

## 7. Логирование
- Логи должны выводиться в консоль и, опционально, в файл.
- Уровни логирования: `DEBUG`, `INFO`, `WARNING`, `ERROR`.
- Ошибки запуска браузера, прокси и профиля должны логироваться отдельно.
- При логировании headers чувствительные значения, включая `Authorization` и `Cookie`, должны маскироваться.
- Логирование содержимого страницы должно быть отключаемым и использоваться только при явном запросе.

## 8. Обработка ошибок
Система должна корректно обрабатывать:
- недоступность прокси;
- отсутствие профиля;
- ошибки запуска браузера;
- неверные аргументы CLI;
- ошибки API-запросов;
- невозможность получить cookies, headers или содержимое страницы;
- отсутствие элемента по заданному локатору;
- неоднозначный поиск, если найдено несколько элементов при ожидании одного;
- невозможность выполнить клик, ввод, выбор значения или отправку формы;
- невозможность выполнить прокрутку или перемещение курсора к указанной точке или элементу;
- выход координат мыши или области случайного движения за допустимые границы страницы или viewport;
- истечение таймаута ожидания элемента, навигации или изменения DOM;
- превышение допустимого размера сохраняемого содержимого.

### Базовые коды ошибок
- Для CLI и API должен использоваться единый каталог кодов ошибок.
- Минимальный набор кодов ошибок должен включать: `INVALID_ARGUMENT`, `UNAUTHORIZED`, `FORBIDDEN`, `SESSION_NOT_FOUND`, `PAGE_NOT_FOUND`, `PROFILE_NOT_FOUND`, `PROFILE_LOCKED`, `PROXY_UNAVAILABLE`, `BROWSER_START_FAILED`, `TIMEOUT`, `ELEMENT_NOT_FOUND`, `ELEMENT_NOT_INTERACTABLE`, `AMBIGUOUS_ELEMENT_MATCH`, `CONTENT_TOO_LARGE`, `INTERNAL_ERROR`.
- Для ошибок API должны быть определены соответствующие HTTP-статусы, например `400`, `401`, `403`, `404`, `409`, `422`, `500`, `502`, `504`.
- Сообщения об ошибках должны быть пригодны для диагностики, но не должны раскрывать секреты и внутренние чувствительные данные.

## 9. Нефункциональные требования
- Версия Python: 3.11+.
- ОС: Linux.
- Код должен быть структурирован по модулям.

- Должен быть определен порядок приоритета конфигурации: аргументы CLI, переменные окружения, конфигурационный файл, значения по умолчанию.
- Должны быть заданы значения по умолчанию для таймаутов, уровня логирования, пути хранения профилей и сетевых параметров API.
- Должны быть определены ограничения на объем сохраняемого HTML, размер логов и число одновременно активных браузерных сессий.

## 10. Документация
- Пользовательская и техническая документация должны быть написаны в формате Markdown.
- Документация должна быть подготовлена на русском и английском языке.
- Вся документация, кроме `README.md`, должна размещаться в каталоге `docs/`.
- Документация должна включать инструкции по запуску через CLI, API и `docker compose`, описание конфигурации, профилей, прокси и примеры типовых сценариев.

## 11. Предлагаемая структура проекта
- `cli/` — консольный интерфейс
- `api/` — HTTP API
- `browser/` — работа с patchright
- `profiles/` — управление профилями
- `proxy/` — интеграция с socks2http
- `tests/` — тесты

## 12. Критерии приемки
Проект считается завершенным, если:
- браузер запускается через CLI;
- браузер запускается через API;
- поддерживается передача User-Agent;
- поддерживается работа через прокси;
- профили создаются и повторно используются;
- cookies могут быть получены через CLI и API;
- headers могут быть получены через CLI и API;
- содержимое страницы может быть получено и сохранено в заданном формате;
- через API можно найти элемент по нескольким типам локаторов;
- через API можно кликать по элементам, заполнять формы и отправлять их;
- через API можно выполнять прокрутку страницы и перемещение курсора, включая случайную траекторию движения;
- через API можно выполнять цепочку действий над страницей с возвратом результата по шагам;
- проект собирается и запускается в Docker;
- Docker-образ собирается на базе `Ubuntu 24.04`, а запуск через `docker compose` выполняется без ручной донастройки контейнера;
- подготовлена OpenAPI-спецификация и документация в `docs/` на русском и английском языке;
- базовые unit- и integration-тесты проходят успешно;
- реализован healthcheck контейнера и endpoint проверки доступности API.
